1. What is SoftyFy?

SoftyFy is a Progressive Web App that streams songs. It is a static frontend (React + Vite) deployed at https://softyfy.onrender.com. The GitHub repository (pradipME/SoftyFy) contains code only — all audio and cover artwork live on Google Drive. A custom Service Worker makes repeat playback instant and offline-capable.

3. Content pipeline — how a song is added

  1. Source selection — a YouTube link or a Spotify album (e.g. Yours Truly, 11 tracks) is chosen and its track list is retrieved (rclone lsjson).
  2. Upload — scripts/drive-upload.mjs uploads the audio file and cover art into the Drive folder with rclone.
  3. Linking — scripts/link-drive-songs.mjs reads Drive file IDs and writes the stream URL + cover URL into frontend/src/data/songs.ts.
  4. Deploy — a push to main triggers an automatic Render redeploy; the Service Worker updates itself on the next visit.

4. The playback fix that made everything work

4.1 The bug

Google Drive's public sharing link (drive.usercontent.google.com/download?id=…) returned HTTP 403 Forbidden in every real browser while working in curl. Root cause: browsers attach Sec-Fetch-Site: cross-site to cross-origin media requests, and Drive's usercontent endpoint rejects any such request. Cover images (thumbnail?id=…&sz=w1000) were NOT affected, only audio.

4.2 The chosen solution

Stream via the official Drive API using a public API key baked into the bundle:

https://www.googleapis.com/drive/v3/files/<FILE_ID>?alt=media&key=AIzaSyAxAkYvJVFy_5HXwvejOlMi0yno613rtK8
  • Honours Range requests (206) and sends permissive CORS headers (ACAO happily echoes softyfy.onrender.com).
  • API keys do not expire; the key is public by design since it ships to every client. Real risks: key deleted/regenerated, or a future Google policy change on the official API.

5. Service Worker — caching design

A hand-written SW (frontend/src/sw.ts) is compiled by vite-plugin-pwa into sw.js. Google does not send cache directives for these streams (cache-control: private, max-age=0, no ETag), so without the SW every play re-downloads the full ~8 MB file — ~350 MB across the library. The SW fixes this while keeping first play fast.

5.1 Audio handler — stream first, cache in background

Audio request flow (per song URL)
  • Cache miss — the Google response is passed through unchanged (streaming), so playback starts immediately. Meanwhile the full body is copied in the background using response.clone() (taken before handover — cloning afterwards throws and used to silently break caching), stored with an x-softyfy-cached-at tag.
  • Cache hit — the single cached file answers any request with correct byte-range semantics (200 full file, 206 exact slice for Range, 416 for out-of-range) so seeking mid-song works perfectly even before downloading the track.
  • Hybrid — seek requests which carry a real Range (mid-stream) pass straight through Google's native range handling.
  • Bounds — max ~8 songs, 14-day freshness, oldest entry evicted. Quota errors are caught silently and playback continues from the network (safe fallback).

5.2 Covers handler

Cached on first sight in softyfy-covers; <img> loads are no-cors/opaque and are stored + served unchanged. (The first workbox CacheFirst route silently never stored them — replaced by the same manual-handler pattern as audio.)

5.3 App shell & updates

Shell assets precached via precacheAndRoute(self.__WB_MANIFEST); skipWaiting() on install + clients.claim() on activate + SKIP_WAITING message → new versions activate instantly, cleanupOutdatedCaches() removes stale caches.

7.2 Notes on a bug found during verification

The first caching attempt eagerly arrayBuffer()-ed the whole file before responding — first play of a new song stalled until ~8 MB downloaded. Fixed to stream-through + background copy; the seek test (which assumed a fully-buffered file) was also updated to reflect real streaming usage.

10. Limitations & trade-offs

  • First listen of a never-heard track downloads the full file in the background even if the user stops after seconds — the deliberate price of instant replays.
  • Cache is capped (≈8 songs) so mobile storage stays bounded; quota exhaustion degrades gracefully to network streaming.
  • The API key cannot be revoked per-client; security comes from the key being public + Drive sharing settings. The main long-term risk is Google policy change, not key expiry.
  • rclone's shared client-id retirement (2026) affects only new uploads, never playback.
