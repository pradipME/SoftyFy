Executive Summary

Modern cloud music streaming platforms (e.g., Spotify, Apple Music, YouTube Music) rely on multi-tier backend infrastructures, subscription paywalls, intrusive tracking telemetry, and continuous cloud connectivity. While these commercial services excel at catalog breadth, users seeking private, personal audio playback face bloated interfaces, recurring costs, and high bandwidth consumption.

SoftyFy is an open-source, serverless, mobile-first Progressive Web Application (PWA) engineered to deliver a Spotify-grade listening experience for personal music collections with zero backend servers, zero databases, and zero user authentication overhead. Built with React 19, TypeScript, Vite, and Tailwind CSS v4, SoftyFy rethinks media distribution by combining an immutable cloud asset CDN (GitHub Releases) with a hand-crafted Service Worker and a patent-quality Measured-Throughput Network Engine.

1. Introduction, Motivation & Scope

1.1 Background & Problem Statement

Personal music streaming typically forces a compromise between two extremes:

  1. Commercial Streaming SaaS: High recurring subscription fees, region locks, intrusive advertisements, battery-heavy background analytics, and licensing disputes that suddenly pull tracks from playlists.
  2. Self-Hosted Media Servers (Navidrome, Plex, Jellyfin): Require 24/7 dedicated server hardware, port-forwarding or reverse proxies (Nginx/Caddy), dynamic DNS configuration, ongoing security patch management, and persistent database maintenance.

Users who already possess curated MP3/M4A music files need a lightweight third option: an instant, private web player that runs entirely in the browser, installs natively on mobile devices, requires zero ongoing maintenance or hosting costs, and streams flawlessly even on degraded cellular connections.

1.2 Project Objectives

  • Zero Cloud Infrastructure Cost: Host the entire static application shell and gigabytes of media assets using free, enterprise-grade public CDNs without maintaining a Node.js/Python server or SQL database.
  • Native Mobile Feel: Recreate Spotify's signature spatial UI: time-of-day greeting, interactive swipe-down "Now Playing" sheet, ambient dynamic background palettes, and persistent bottom navigation.
  • Network Resilience & Adaptive Quality: Guarantee immediate audio playback (<1.5s startup) across varying mobile networks (2G/3G/4G/5G) using intelligent measured-throughput bitrate switching (HQ vs LQ).
  • Zero Replay Bandwidth: Ensure that once a song or cover is played, repeat listens incur 0 MB of outbound network traffic via deterministic client-side service worker caching.
  • System-Level Media Control: Integrate seamless lockscreen notifications, smartwatch remote controls, and automotive Bluetooth playback via the W3C MediaSession API.

2. Architecture & Technology Stack

SoftyFy utilizes a decentralized, client-first architecture where the browser client acts as the complete orchestrator. The server layer is entirely static, serving only pre-compiled assets.

Figure 2.1: SoftyFy End-to-End System Architecture

2.1 Component & State Architecture

The core playback state is managed in a strictly typed React Context (PlayerContext.tsx) backed by a pure state reducer (playerReducer.ts). This ensures deterministic state transitions without race conditions:

  • Single Shared Audio Element: Rather than re-mounting audio elements on page navigation, SoftyFy attaches a single persistent <audio> element to the document body. Navigating between Home, Search, and Library never interrupts the audio stream.
  • Action Decoupling: The reducer manages queue ordering, shuffle permutations (preserving the original queue while indexing via playOrder), repeat modes (off, all, one), volume, and explicit user intent (playIntent).
  • Adaptive Quality State: Tracks streamingQuality (user preference: auto, high, low) and currentQuality (actual resolved tier and forensic explanation string).

3. Media Storage Evolution: The Cloud Journey

Hosting over 100 high-bitrate audio files (~1 GB) in a static project without a backend server posed the single greatest technical challenge of the project. The architecture underwent three distinct evolutions before reaching enterprise stability.

3.1 The Three Storage Phases

Phase 1: Local File Ingestion (Git Bloat)
Initial prototypes bundled MP3 files directly inside frontend/public/audio/. While simple, pushing ~350 MB to GitHub caused repository bloat, slow cloning, and risked exceeding GitHub's 100 MB per-file and 1 GB repository soft limits.
Phase 2: Google Drive API & The Cross-Site 403 Nightmare
To decouple media from the repository, files were uploaded to Google Drive via rclone, and streaming URLs were constructed using Drive's download endpoints.
The Bug: While curl and Node scripts successfully downloaded audio, real web browsers failed with HTTP 403 Forbidden. Modern browsers attach the security header Sec-Fetch-Site: cross-site to media requests. Google's public download servers reject cross-site audio stream requests.
The Intermediate Fix: Switching to the official Drive API v3 endpoint: 
https://www.googleapis.com/drive/v3/files/{FILE_ID}?alt=media&key={API_KEY}
This supported Range requests and sent permissive CORS headers. However, Google soon flagged public API keys for excessive quota consumption, and key rotation scripts proved fragile.
Phase 3: The Production Solution — GitHub Release Assets CDN (softyfy-audio-v1)
The ultimate architectural breakthrough was utilizing GitHub Release Assets as an immutable, high-bandwidth Content Delivery Network: 
https://github.com/pradipME/SoftyFy/releases/download/softyfy-audio-v1/{TRACK_FILENAME}.mp3
Why this succeeded:
  • Native HTTP 206 Partial Content: GitHub's underlying asset storage (Amazon S3 / Azure CDN) fully supports byte-range requests, allowing instant scrubbing to any second of a track.
  • No Key Expiration or Quotas: Public release downloads carry no per-day API key rate limits or billing triggers.
  • Permanent Immutability: Asset binaries never mutate, making them ideal for long-term browser and Service Worker caching.

4. Service Worker & Offline Byte-Range Slicing

Standard browser Service Worker implementations built with standard Workbox CacheFirst strategies fail when applied to audio media. Browsers stream audio in chunks via Range: bytes=0- headers; a naive cache either refuses to store opaque partial responses or re-downloads the entire file on every seek.

4.1 The Custom Audio Stream Interceptor (sw.ts)

SoftyFy implements a specialized Service Worker (frontend/src/sw.ts, 645 lines) compiled using vite-plugin-pwa with injectManifest.

Figure 4.1: Service Worker Audio Pipeline & Slicing Logic

4.2 Key Engineering Innovations in sw.ts

  • Stream-Through First Play: Previous iterations attempted to await response.arrayBuffer() before serving. This stalled audio start times by 6–10 seconds. The current design streams the original fetch directly to the audio element while asynchronously pumping a cloned stream into the Cache Storage.
  • In-Flight Skip Cancellation: If a user skips tracks rapidly, multiple 8 MB downloads would saturate mobile bandwidth. SoftyFy stores an AbortController for each active fill. Skipping to a new song immediately cancels previous background cache fills.
  • Synthesized Byte-Range Slicing (buildRangeResponse): When a cached song is scrubbed, the service worker parses the Range: bytes=start-end header, calculates the byte offsets over the cached ArrayBuffer, and responds with status code 206 Partial Content, Content-Range, and correct headers.
  • Active Playback Protection: The cache eviction routine maintains an activeUrls registry. A song currently playing is never evicted, even if the user navigates through multiple other tracks.

5. Adaptive Bitrate & The Network Memory Engine

Streaming 320 kbps high-definition audio on mobile devices frequently causes audio stuttering due to cellular handover and fluctuating coverage. SoftyFy introduces a custom adaptive bitrate system built on real-world session measurements.

5.1 The Fallacy of navigator.connection

Initial attempts to adapt bitrate relied on the W3C Network Information API (navigator.connection.effectiveType). Field testing revealed a fatal flaw: on a smartphone with weak cellular reception (e.g., 1 bar of 4G or congestion), navigator.connection continues to report effectiveType: "4g" and a high nominal downlink. Relying on this API caused the player to load 320 kbps files, resulting in buffer underruns and playback stalls.

5.2 Measured-Throughput Session Memory (networkMemory.ts)

SoftyFy abandons theoretical connection hints in favor of two zero-cost empirical signals produced naturally by the browser's media element:

  1. Time-to-Buffer (timeToBufferMs): Elapsed milliseconds from load initiation until 5 seconds of media runway is buffered ahead (measured via audio.buffered).
  2. Playback Stalls: Count of waiting and stalled events fired by the media element during track playback.
Figure 5.1: Network Memory State Machine & Hysteresis Loop

5.3 The Hysteresis Algorithm

To prevent rapid flip-flopping between high and low quality on edge-case connections:

  • Immediate Downgrade: If a track stalls twice or takes >4,000ms to buffer 5s of runway, the session is instantly marked weak = true, immediately routing the subsequent songs to their low-bitrate (-lq.mp3) twin.
  • Hysteresis Recovery: Leaving the weak state requires 3 consecutive comfortable loads (goodStreak >= 3). A comfortable load on LQ means filling the 5s buffer in <800ms.
  • Cache Immunity: Loads completing in <150ms are identified as cache hits and classified as neutral; they cannot falsely advance the recovery streak.
  • User Override: The user can select Auto, High, or Low in the player UI. A manual setting strictly overrides network heuristics.

6. Mobile-First UX, Gestures & Lockscreen Integration

6.1 Spatial UI & Expandable Now Playing Sheet

The application user interface is modeled directly after the modern Spotify mobile experience, featuring a dark chromatic palette (#0a0a0c background with glassmorphic cards and #6366f1 violet accents).

  • Persistent Mini Player: Anchored directly above the bottom navigation bar on mobile viewports. It exposes immediate track details, play/pause toggles, and animated progress indications.
  • Swipe-to-Dismiss Fullscreen Sheet: Tapping the mini player smoothly expands a fullscreen view (NowPlayingSheet.tsx) powered by Framer Motion. Users can swipe down with touch velocity gestures or press Esc to collapse the player.
  • Dynamic Ambient Canvas: The background dynamically reflects the dominant palette extracted from the currently playing album cover (coverColors.ts), rendering a blurred, animated atmospheric glow.

6.2 System Lockscreen Integration via MediaSession API

To guarantee a true native application experience when the phone screen is locked or the browser is minimized, SoftyFy synchronizes with the W3C navigator.mediaSession API: 

navigator.mediaSession.metadata = new MediaMetadata({
  title: activeSong.title,
  artist: activeSong.artist,
  album: activeSong.album || activeSong.library,
  artwork: [
    { src: activeSong.coverSrc, sizes: '512x512', type: 'image/jpeg' },
    { src: activeSong.coverSrc, sizes: '192x192', type: 'image/jpeg' },
  ],
})

Action handlers are registered for play, pause, previoustrack, nexttrack, seekto, and seekbackward / seekforward. System lockscreens, Apple Watch controls, and Android auto infotainment systems display song metadata and interactive scrubber bars.

6.3 Screen-Off Auto-Advance Resilience

Mobile operating systems (particularly iOS Safari and aggressive Android OEM battery managers) throttle JavaScript timers (setTimeout, setInterval) when the screen turns off or the browser is backgrounded.

Engineering Solution: Rather than relying on polling intervals to detect track end, SoftyFy registers native DOM ended listeners directly on the audio element, augmented with onNativePlaybackAction hooks and page visibility listeners (document.addEventListener('visibilitychange')). The player queues the next track synchronously upon the ended event, ensuring background playlists never stop.

8. Engineering Challenges, Pitfalls & Trade-offs

8.1 Why Capacitor Android APK Was Dropped in Favor of Pure PWA

During mid-September development, an experimental branch introduced Capacitor to build and compile SoftyFy into a native Android APK (feat(capacitor): ship SoftyFy as a native Android APK).

The Architectural Conflict:
  • Capacitor introduced a heavyweight Android build toolchain (Gradle, Android Studio, Java SDK, NDK), defeating the minimalist "zero-server, zero-overhead" project ethos.
  • Native WebView media players handle Service Worker intercepted requests inconsistently, breaking synthesized byte-range slicing on older Android versions.
  • Modern mobile browsers (Chrome on Android, Safari on iOS) already support 100% of the required native capabilities via standalone PWAs: homescreen icon, splash screen, MediaSession lockscreen controls, and offline storage.
  • Decision: Reverted Capacitor and focused exclusively on a pristine, zero-dependency Progressive Web App.

8.2 Preventing Background Cache Contention with Live Playback

When a song starts playing on a slow network, the browser audio element requests the first 500 KB to begin playback, while the Service Worker begins fetching the full 8 MB file to store in cache.
The Problem: The background cache fetch competed with the live playback stream for network socket bandwidth, stalling audio startup.
The Solution: Implemented in-flight download pacing. On weak networks, background full-file cloning is throttled or deferred until the audio element has successfully buffered 5 seconds ahead.

8.3 Web Audio API Routing vs Mobile Autoplay Restrictions

An experiment with real-time canvas visualizers used the Web Audio API's AudioContext.createMediaElementSource().
The Bug: Mobile browsers enforce strict user gesture requirements on AudioContext. Routing audio through an un-resumed Web Audio graph completely muted playback on iOS and Android.
Resolution: Decoupled visualizer loops, ensuring AudioContext.resume() is invoked strictly inside user touch events, with fallback to native element playback if audio nodes fail.

9. Conclusion, Roadmap & References

9.1 Project Conclusion

The SoftyFy project demonstrates that a commercial-grade, responsive, and resilient media streaming platform can be built completely without backend servers, databases, or recurring cloud costs. By leveraging modern browser APIs (Service Workers, MediaSession, Web Storage), immutable public CDNs (GitHub Releases), and measured-throughput network intelligence, SoftyFy achieves high reliability, instant playback, and zero-cost hosting.

9.2 Future Roadmap

  • Synchronized LRC Lyrics: Parse and render karaoke-style synchronized lyrics with smooth auto-scroll.
  • Origin Private File System (OPFS): Utilize OPFS for dedicated offline storage exceeding standard Cache Storage quotas.
  • Web Audio Equalizer: Re-introduce a 5-band parametric equalizer safely routed through user-gesture audio graphs.
  • Client-Side ID3 Metadata Ingestion: Enable drag-and-drop ingestion of local audio files directly into browser IndexedDB.
